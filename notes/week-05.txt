Corpus & Chunking Configs
Built an 8-document corpus for a fictional "Orbit" server (networking, storage, replication, limits, security, backup, monitoring, deployment), short enough that ground truth stays easy to check by hand.
Compared three chunking configs instead of multiple embedding models: small (120 chars/20 overlap) -> 22 chunks, large (320/40) -> 9 chunks, and by-paragraph -> 8 chunks.
Found a bug in the large config's own chunker while investigating why it tied exactly with by-paragraph: the fixed-size loop doesn't stop cleanly when what's left over is smaller than the overlap, so the backup doc gets a second, near-empty junk chunk ('yaml.'). Confirmed it never lands in any query's top-3, so it doesn't affect the numbers, but it's a real bug worth naming rather than a rounding coincidence.
 
Retrieval Pipeline
Embedded chunks locally with sentence-transformers (all-MiniLM-L6-v2, no external API) and indexed them with FAISS's IndexFlatIP over normalized vectors, so inner product equals cosine similarity.
Verified the retrieval and precision/recall arithmetic first against a fake bag-of-words embedder before ever touching the real model, to separate plumbing bugs (indexing, top-k search) from actual embedding quality.
 
Chunk-Level Precision/Recall Setup
Ground truth is decided in advance: each of 14 queries has a pre-written answer fact, and a chunk counts as relevant iff it contains that fact. The fact strings were fixed before any chunking config was run, so the criterion doesn't shift per config even though the resulting chunk ids do.
Computed precision@3 and recall@3 per config by checking, for each query, how many of the top-3 retrieved chunks fall in that query's relevant set.
 
Evaluating Fourteen Queries
Ran all 14 queries (>= 10 required) against each of the three configs:
small (120/20)   precision@3=0.40  recall@3=0.94
large (320/40)   precision@3=0.36  recall@3=1.00
by-paragraph     precision@3=0.36  recall@3=1.00
large and by-paragraph tie because every doc here is short enough that both configs land near one chunk per doc. small moves in both directions at once: it loses some recall (a fact gets cut across a chunk boundary and neither half alone is a full match) but gains precision (splitting each doc into 2-3 pieces lets more than one relevant chunk from the same doc land in the top-3 together, something a one-chunk-per-doc config can never do).
 
Failure Case
Under small (120/20), the monitoring doc's sentence "Health checks are available at /healthz on the same port" lands right on a chunk boundary. Confirmed first with plain string matching, no model involved: chunk A ends "...available at /heal", chunk B starts "e available at /healthz...", and neither contains the whole phrase. large and by-paragraph don't have this problem for this corpus -- checked the same way.
Then ran it live: asked "where can i check server health" against small (120/20). Both halves of the split sentence actually made it into the top-3, so retrieval wasn't missing anything. The problem showed up in generation instead -- the model read the truncated "/heal" in chunk A and answered with it as a second, real endpoint, alongside the correct /healthz. The "answer only from context" instruction likely made this worse, since it pushes the model to take whatever text is in front of it at face value rather than asking whether "/heal" looks like a complete path.
