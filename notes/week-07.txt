Week 7 process notes: what I did and what surprised me
=======================================================
Companion to the research note. The research note says what the results show; this one records how both notebooks were built and checked, and the things that went wrong or turned out to be interesting along the way.

HOW THE NOTEBOOKS WERE BUILT
----------------------------
Generator scripts. Each notebook is produced by a Python script (build_notebook.py, build_banking.py) that holds the cell text and writes the .ipynb. The script is the source of truth, so a fix is made once and the notebook is rebuilt, instead of hand-editing JSON.
Tested against fakes before touching Colab. A test script executes the notebook's real cell source against stand-ins for the embedder, FAISS, the tokenizer, the Anthropic client and the CSV downloads. This proves the plumbing and nothing else: every number and every claim about what the model does comes from the Colab run, because the build environment can neither reach Hugging Face nor call the Anthropic API.
Scenarios, not just the happy path. The tests cover a normal run, a repeat run for determinism, no API key, no tiktoken, a transient failure with retry, a bad key that must fail fast, the API refusing the temperature setting, a failed download, and a missing intent. The Banking77 test feeds in fake CSVs with known defects (3 duplicates, 2 whitespace repairs, 1 empty message, 2 overlong, 2 train/eval leaks, 1 conflicting pair) and asserts the exact cleaning counts (909 raw rows to 899 clean).
Statistics written by hand and checked against known values. Accuracy, macro-F1, an exact two-sided sign test and Wilson 95% intervals are implemented in a few lines each, with sanity checks: the sign test gives 1.0 for (0,0), 0.0625 for (5,0), 1.0 for (3,3) and 0.34375 for (7,3), and Wilson for 50/100 is [0.4038, 0.5962].
Fixed once, compared fairly. Every (variant, message) pair is called exactly once and cached, so zero-shot and few-shot are compared on one fixed set of outputs. Temperature is pinned to 0. A failed call is never cached and never scored as wrong, and a prediction that cannot be parsed to a valid label counts as wrong but is reported separately. The same instruction line is used with and without examples, so the retrieved examples are the only difference.
Decisions made before looking. In the synthetic notebook, some eval templates are held out of training and two hard ticket kinds are tagged before any model call. In both notebooks the slices (by kind, template, label, cluster, intent, top-1 neighbor relation and retrieval purity) are defined by the data and retrieval, not by who won. Anything added after seeing results (the stress test, the definitions) is labeled as post hoc.
Data engineering. The cleaning steps are whitespace repair, dropping empty and overlong messages, dedup on a normalized key, dropping groups of identical text with conflicting labels, and removing train messages that also appear in eval. A short hash of the cleaned data (the fingerprint) lets a Colab run be compared with the build environment's.

THINGS THAT WENT WRONG, AND WHAT THEY TAUGHT US
-----------------------------------------------
The fake client was too forgiving. It accepted temperature=0, but the real SDK (1.5.0) has no such argument, so Colab raised TypeError: Messages.create() got an unexpected keyword argument 'temperature'. The fix sends it through extra_body, with a fallback if the API refuses it. The test client now rejects any argument the real signature does not have, and I verified the request body offline. A fake that is looser than the real thing hides exactly the bug it should catch.
It looked stuck, but it was failing slowly. Part 3 sat on "ticket 0/64" for ten minutes. The log later showed 16 failed calls after 8 tickets and 112 seconds: the temperature error was being retried with sleeps, and the progress line was too sparse to show it. The fixes: a smoke-test call before the loop, no retry on 400/401/403/404, a 30-second timeout, progress every 4 tickets, and an abort after 3 consecutive failed tickets. The user was also running an older notebook version, which is why rebuilding and versioning the files mattered.
The generator under-produced one label. account_access templates yielded too few distinct cores (34 against the 50 intended), which would have left only 58 eval tickets. Widening the templates and adding a gadget slot brought eval to 64.
Two overclaims caught before they shipped. I had called the definitions prompt "cheaper"; the data showed it adds more tokens than 4 retrieved examples (223 vs 194 vs 103 for names only). And the latency in the synthetic Results table was stale (0.53/0.51s from an earlier run, against 0.63/0.65s in the final one).
A redundant-call bug in the label-noise experiment. A ticket with no flipped example gets the identical prompt as the clean few-shot run, so calling the API again would only add random differences. Those tickets now reuse the clean answer.

INTERESTING FINDINGS
--------------------
An eval at the ceiling is a finding about the data. Zero-shot got 98.4% on the template tickets, so there was nothing for few-shot to fix or break, and even a deliberate stress test (30 tickets where the vote of the retrieved examples was wrong by construction) did not make it fail. Switching to real messages was a better answer than engineering ever-harder synthetic ones.
Retrieval is not the same as understanding. The no-LLM kNN vote misses held-out phrasings because embeddings match topic words ("cancel", "billing"), not what the customer asks for. Yet few-shot got those same tickets right even when all four neighbors carried the wrong label, so the model read the ticket and did not copy.
The few-shot gain on Banking77 was mostly a labeling convention. Seven of the nine few-shot-only wins are one intent, card_arrival, where this dataset files "tracking number" questions. Zero-shot sees only the intent names, so it sent them to card_delivery_estimate (25% on that intent, against 83% with examples). A one-line definition raised it to 92%. The examples were teaching dataset conventions, not general knowledge.
The cheaper-looking rival was not cheaper. Definitions saved infrastructure (no labeled set, embedder or index) but cost more tokens per message than retrieved examples.
Unparseable replies were the model declining. The definition prompts returned a non-intent reply on 7 of 240 calls; six of the seven printed replies said the message fits none of the intents. Counting them as wrong is fair for a forced-choice score, but in a real router "doesn't fit" is a useful answer. One reply was cut off by the 24-token limit before it chose, a reminder to check a limit against real outputs.
Few-shot lost twice, both times against correct examples. In the not_working group (34 vs 32 of 36) all four retrieved examples were right in both misses, and we could not explain why. Because it is stable at temperature 0, it is not sampling noise, but it is two messages and within noise.
The cheapest method scored highest. A plain vote of the four nearest neighbors reached 95.8% with no model call. Part of that is Banking77's near-paraphrases (20 of 120 eval messages have a training neighbor at similarity 0.95 or higher), which favor retrieval.
Some "errors" look like label problems. declined_transfer was weak for every method, and one message about a declined online card purchase is labeled declined_transfer. We read one example, not an audit, so this is a lead rather than a result.

DISCLOSED LIMITS
----------------
- All results are from single runs; the Banking77 eval is 120 messages, so one message moves accuracy by about 0.8 points.
- The synthetic stress test covers 7 of 15 phrasings I wrote, and one phrasing made up 11 of the 30 tickets.
- The label-noise experiment is built and tested against fakes but has not been run on the real API.
- The definitions were written after seeing the first results, so those rows are optimistic.
