Week 6 RAGAS evaluation experiment
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Pipeline & Methodology
Evaluated the Week 5 Orbit RAG pipeline, fixed to a single configuration rather than comparing multiple: small (120/20) chunking, top-3 retrieval, Claude (claude-haiku-4-5-20251001) generation. Picked this config deliberately over the better-scoring large/by-paragraph options from Week 5, since it's the one with an already-known real failure (the /healthz chunk split from Part 4) -- evaluating the best-performing config would have made for a low-signal test with nothing real to find.
Implemented the four RAGAS dimensions directly with Claude as an LLM judge rather than installing the ragas package, which defaults to OpenAI and would need an extra LangChain/Anthropic wrapper for no real benefit, since the published definitions are what actually matter. Each metric follows RAGAS's own methodology: faithfulness and context recall decompose text into atomic claims and verify each against the context; answer relevancy generates synthetic questions from the answer and measures embedding similarity to the real question; context precision gets per-chunk relevance verdicts and computes rank-weighted average precision.
 
Verification Before the Live Run
Tested all four metric functions against a scripted fake judge before ever calling the real model -- covering JSON-parsing edge cases (prose-wrapped JSON, code-fenced JSON), the exact rank-weighted precision formula against a hand-computed expected value, and zero-claims edge cases (a claim-free answer should score vacuously faithful, not divide by zero). Then re-ran the actual notebook cell code (not just the dev script) against a fake judge and fake embedder to confirm nothing broke in translating from the test script into the notebook. Both passed cleanly, so the scoring arithmetic was confirmed correct before any real judgment was trusted.
 
Queries & Scores
Ran six queries (five required): three single-fact, two compound (asking for two facts at once), and the known /healthz query from Part 4, each with a ground-truth reference answer decided in advance from the doc text.
Real results: faithfulness 1.00, answer relevancy 0.78, context precision 1.00, context recall 0.92. Context recall's one weak point (0.50) was the same near-miss identified in Week 5 Part 2 -- a fact stated twice in the networking doc, only one occurrence retrieved.
 
Weakest Dimension: Answer Relevancy
Per-query scores showed a clean pattern: short, direct single-sentence answers scored highest (0.82-0.84); longer, hedged, or heavily formatted answers scored lowest (0.66 on a query where Claude correctly said the context didn't fully specify an answer; 0.75-0.79 on the two compound questions, both answered with bolded sub-headers). Since the metric works by generating synthetic questions from the answer and comparing them to the real question via embedding similarity, scaffolding that isn't direct answer content -- caveats, restated headers, "based on the context" framing -- pulls the synthetic questions away from the original phrasing, even when the answer is substantively correct. The failure mode is verbosity diluting directness, not wrong information.
 
A Second Finding: Faithfulness's Blind Spot
Faithfulness scored a perfect 1.00 on every query, including the /healthz query with the known chunk-split hallucination (Claude answers with two endpoints, /healthz and /heal, when there's only one). The claim "a /heal endpoint exists" is technically grounded in the truncated chunk's literal text, so the judge correctly marks it as context-supported while missing that the claim itself is false. This is a real limitation of faithfulness as RAGAS defines it: grounded-in-context and true-in-the-world aren't the same thing, and this run is direct evidence of where they diverge. Worth noting since it wasn't something the numbers alone would surface -- only looking at the per-query detail caught it.
 
Proposed Fix & Tradeoffs
Tighten the generation prompt to require a direct, single-paragraph answer -- no restated question headers, no bullets for simple facts, no "based on the context provided" framing. Targets answer relevancy specifically, since cutting non-answer scaffolding should pull the reverse-engineered questions back toward the original phrasing.
Cost is close to free -- a prompt edit, not an added model call or retrieval change. The real risk is qualitative: the lowest-scoring answer hedged because the docs genuinely lacked detail, and that hedge was accurate. Pushing toward shorter, more confident-sounding answers risks trading honest uncertainty for a better-looking score rather than better actual quality -- a fix that chases the metric instead of the thing the metric is supposed to measure.

Extended Week 5's retriever with HyDE plus a hybrid dense+lexical re-ranker. Same corpus, same 14 queries, same small (120/20) chunking as Week 5, so results are comparable.

Real results: baseline precision@3=0.381/recall@3=0.964, HyDE alone 0.286/0.750, HyDE+rerank 0.310/0.821. HyDE never improved a single query — 0 improved, 3 regressed, 11 unchanged. Re-ranking recovered some but not all of the damage.

Found two different failure causes behind two similar-looking regressions. For "/healthz," HyDE invented a fake URL and the right chunk never even made it into the retrieved candidate pool — a transformation-stage loss. For "quorum," the right chunk was in the pool but still lost the re-rank — a re-ranking-stage loss. Confirmed this by directly checking the candidate pools rather than assuming from the score drops.

Optional Part 4: added schema-constrained extraction (Claude tool-use forcing a port/limit/setting schema) to answer a count query and a cross-doc comparison that plain retrieval struggles with. Both answers came out correct. Checked empirically whether vector search actually failed each query — it did for the count query (missed a needed doc), but not for the comparison query (got lucky and retrieved both needed docs anyway).

Findings:

HyDE only had room to hurt here, not help. Baseline retrieval was already near ceiling (recall@3 0.964), so there was nothing for a paraphrase step to gain and plenty for it to lose if the generated guess was wrong.

A confident, specific, wrong hypothetical is worse than a vague one. Telling the model not to hedge traded a safe "I'm not sure" for fabricated specifics (a made-up URL, the wrong consistency term) that embed nowhere near the real answer.

Two regressions that looked identical by the numbers had different root causes, and that only showed up by checking the actual candidate pool, not the score deltas. This matters practically: the fix for one (merge in the raw query's own retrieval so a bad guess can't exclude the right chunk) wouldn't have fixed the other (a re-ranker weighting issue).

Don't force a clean story onto mixed evidence. Part 4's "vector search can't do this" claim only held for one of the two test queries when actually checked — reporting that honestly was more useful than claiming both proved the point.
